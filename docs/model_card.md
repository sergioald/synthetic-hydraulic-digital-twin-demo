# Model card: Synthetic hydraulic digital-twin workflow

## Model name

Synthetic Hydraulic Digital Twin Demo

## Version

This model card describes the public synthetic workflow after the addition of
scenario configurations, validation-scope documentation and optional HTML
report generation.

## Summary

This repository implements a synthetic, digital-twin-style workflow for
hydraulic sensor data. It generates synthetic sensor time series, validates
sensor structure and ranges, derives engineering features, estimates energy
use, flags anomalies, classifies operating states and produces Markdown or
HTML reports.

The workflow is designed for public demonstration, teaching, portfolio review
and research-software discussion. It is not a calibrated hydraulic simulator
and is not an operational condition-monitoring product.

## Intended use

Appropriate uses include:

- demonstrating applied AI for engineering sensor systems;
- showing a reproducible digital-twin-style software architecture;
- teaching sensor validation, feature engineering and anomaly-detection
  workflow design;
- portfolio review by recruiters, collaborators or research-software reviewers;
- testing documentation, reporting and scenario-configuration patterns with
  fully synthetic data.

## Out-of-scope use

This workflow must not be used for:

- operational monitoring of a real hydraulic facility;
- safety-critical decisions;
- automated maintenance decisions;
- real fault diagnosis;
- estimating the health of real pumps, actuators, structures or control systems;
- claiming validation against real FastBlade, University of Edinburgh, partner
  or industrial data.

## Users

Expected users are:

- technical reviewers;
- applied-AI researchers;
- engineering researchers;
- students learning digital-twin workflow design;
- recruiters assessing software and applied-ML capability.

The repository is not intended for operators using it as a live monitoring tool.

## Data

The workflow uses fully synthetic data generated by code in the repository.

The repository does not contain:

- real FastBlade data;
- real University of Edinburgh code;
- partner or industrial datasets;
- proprietary control logic;
- real facility diagrams;
- real hydraulic parameters;
- real sensor exports;
- confidential reports or database schemas.

Synthetic variables include pressure, flow, power, temperature, command,
load, displacement, vibration proxy and event labels. These variables are
illustrative and should not be interpreted as real facility measurements.

## Inputs

The main input is a YAML configuration file. The configuration controls:

- simulation duration;
- sampling interval;
- random seed;
- synthetic system ranges;
- energy-model assumptions;
- anomaly-detection settings;
- synthetic event inclusion.

Scenario-specific YAML files are provided in `configs/scenarios/`.

## Outputs

The workflow can produce:

- a synthetic CSV dataset;
- a Markdown report;
- an optional self-contained HTML report;
- anomaly flags;
- digital-twin state labels;
- state-reason labels;
- validation messages;
- engineering-style recommendations.

## Model and workflow details

The workflow combines deterministic engineering-style calculations, transparent
rules and a simple unsupervised anomaly-detection baseline.

Main stages:

```text
synthetic data generation
→ sensor validation
→ feature engineering
→ hydraulic/electrical energy estimation
→ anomaly detection
→ digital-twin state classification
→ Markdown/HTML report generation
```

The anomaly layer combines rule-based checks and an Isolation Forest baseline.
The state-classification layer maps validation, anomaly and derived feature
signals into interpretable labels.

## Evaluation

The repository includes software tests for:

- synthetic data generation;
- validation checks;
- feature engineering;
- energy estimation;
- anomaly detection;
- state classification;
- report generation;
- CLI smoke execution;
- scenario-configuration execution.

These tests verify software behaviour and reproducibility. They do not validate
physical accuracy or operational diagnostic performance.

## Performance

No real-world diagnostic performance is claimed.

Because the data are synthetic and the labels are generated by the same public
workflow, metrics such as operational false-positive rate, false-negative rate,
precision, recall or maintenance benefit are not reported.

## Limitations

Important limitations:

- synthetic signals are illustrative;
- thresholds are not operationally calibrated;
- event labels are generated by the synthetic data generator;
- no real sensor export format is validated;
- no uncertainty propagation is included;
- the Isolation Forest baseline is illustrative;
- state labels are review categories, not diagnostic truth;
- recommendations are synthetic decision-support text, not instructions.

## Ethical and safety considerations

The repository is designed to avoid exposing confidential or sensitive
industrial/research information. The main risk is over-interpretation: readers
may mistake a synthetic workflow for an operationally validated digital twin.

To reduce this risk, the README, reports, model card and validation-scope
documentation all state that the repository uses synthetic data only and is not
suitable for safety-critical decisions.

## Maintenance

Future maintenance should prioritise:

- keeping the synthetic-data boundary explicit;
- avoiding real or confidential data in examples;
- preserving tests for CLI, reporting and scenarios;
- documenting any new assumptions;
- updating this model card when workflow outputs or intended use change.
