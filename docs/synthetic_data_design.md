# Synthetic Data Design

This document describes the synthetic data design used by the `synthetic-hydraulic-digital-twin-demo` repository.

The purpose of the synthetic data generator is to create a realistic-enough engineering monitoring dataset for demonstrating data validation, feature engineering, energy estimation, anomaly detection, digital-twin state classification and automated reporting. It is not intended to reproduce a real hydraulic rig, real control system or real facility.

## Publication boundary

All data generated by this project is synthetic.

The repository does not include:

- real FastBlade data;
- real University of Edinburgh code;
- real facility diagrams;
- partner or industrial datasets;
- proprietary control logic;
- real sensor exports;
- real component parameters;
- real operating limits;
- real maintenance or failure records.

Any similarity between the synthetic signals and a real hydraulic system is illustrative and non-operational.

## Design goals

The synthetic generator is designed to support a public applied-AI portfolio project. The main goals are:

1. **Safety**: avoid publishing confidential or facility-specific information.
2. **Reproducibility**: generate the same dataset from the same configuration and random seed.
3. **Engineering plausibility**: produce signals with relationships that make sense for a generic hydraulic monitoring example.
4. **Model-testing utility**: inject known synthetic events so that anomaly detection and state classification can be tested.
5. **Readability**: keep the implementation simple enough for a reviewer to understand quickly.

## Synthetic system abstraction

The public abstraction is a simplified sensor-heavy hydraulic monitoring workflow:

```text
reservoir
→ auxiliary/low-pressure supply
→ conditioning stage
→ hydraulic pump/motor unit
→ pressure storage element
→ structural load interface
→ return path
```

This is a generic abstraction. It is not a hydraulic schematic and must not be interpreted as a representation of any real facility.

## Core synthetic signals

The generator creates a time-indexed dataset with signals such as:

| Signal | Purpose |
|---|---|
| `timestamp` | Simulated measurement time |
| `reservoir_level_pct` | Synthetic reservoir level indicator |
| `low_pressure_bar` | Synthetic low-pressure line measurement |
| `low_pressure_temperature_c` | Synthetic low-pressure oil temperature |
| `flow_lpm` | Synthetic hydraulic flow rate |
| `high_pressure_bar` | Synthetic high-pressure output measurement |
| `return_pressure_bar` | Synthetic return/low-pressure input measurement |
| `motor_power_kw` | Synthetic electrical power drawn by the motor |
| `motor_speed_rpm` | Synthetic motor speed |
| `motor_temperature_c` | Synthetic motor temperature |
| `accumulator_pressure_bar` | Synthetic pressure-storage measurement |
| `accumulator_temperature_c` | Synthetic oil temperature near pressure storage |
| `command_signal_pct` | Synthetic demand/control signal |
| `load_demand_kn` | Synthetic structural load demand |
| `actuator_displacement_mm` | Synthetic actuator displacement proxy |
| `vibration_proxy` | Synthetic vibration/audio-like monitoring proxy |
| `event_label` | Synthetic ground-truth event label for examples and tests |

The variables are intentionally generic. They should be interpreted as public demonstration variables rather than real sensor names.

## Signal construction

The generator starts from a synthetic command signal. The command signal is created from smooth periodic components plus random noise. Other measurements are then generated as noisy functions of the command signal.

At a high level:

```text
command_signal_pct
→ demand_fraction
→ pressure, flow, motor speed, load demand
→ hydraulic power and motor power
→ temperatures, vibration proxy and storage pressure
```

This produces a dataset where signals are correlated in useful ways. For example, higher demand generally produces higher pressure, higher flow, higher motor power, higher load demand and increased temperature. Random noise is added so that the data does not look artificially perfect.

## Synthetic events

The generator can inject synthetic operating events. These are configured in `configs/default.yaml`.

| Event | Synthetic behaviour |
|---|---|
| `normal` | Baseline operation generated from the normal demand cycle |
| `inefficient_regime` | Motor power and temperature increase relative to demand |
| `sensor_drift` | High-pressure signal gradually drifts upward |
| `missing_data` | Critical pressure/flow values are set to missing for a short period |
| `pressure_loss` | High pressure drops while flow and return pressure change |
| `pump_degradation` | Motor power, temperature and vibration proxy gradually increase |
| `abnormal_energy` | Motor power spikes for a short interval |
| `load_anomaly` | Load demand and displacement behaviour become inconsistent |
| `transient_event` | Short oscillatory pressure/vibration disturbance |

These events are deliberately simple. Their role is to make the pipeline testable and explainable, not to simulate real physics.

## Event labels and model use

The `event_label` column is synthetic ground truth. It is useful for:

- demonstrating the generated scenarios;
- writing tests;
- checking whether anomaly-detection outputs are plausible;
- explaining the example report.

The anomaly detector should not rely on `event_label` as an input feature. In a real monitoring setting, ground-truth failure labels are often sparse, delayed, incomplete or unavailable. For this reason, the project keeps the event labels separate from the detection logic.

## Configuration

The main configuration file is:

```text
configs/default.yaml
```

It controls:

- simulation duration;
- sampling interval;
- random seed;
- broad synthetic ranges;
- energy-model constants;
- anomaly-detection parameters;
- which synthetic events are included.

All configuration values are illustrative. They should not be interpreted as real operating limits or component parameters.

## Reproducibility

The generator uses a random seed. With the same configuration and seed, it should produce the same synthetic dataset. This is important for:

- reproducible examples;
- stable tests;
- consistent documentation outputs;
- fair comparison of future model changes.

## Known limitations

This generator is intentionally lightweight. It does not include:

- physics-based hydraulic simulation;
- component-level fluid dynamics;
- calibrated pump curves;
- real controller behaviour;
- real failure distributions;
- uncertainty propagation;
- sensor calibration metadata;
- time synchronisation errors beyond simple missing data.

Those limitations are acceptable for the current purpose: a safe public demonstration of applied-AI and digital-twin workflow design.

## Future improvements

Possible future improvements include:

- richer synthetic operating modes;
- configurable event start/end times;
- synthetic sensor bias and calibration metadata;
- multiple independent test runs;
- synthetic train/test scenario splits;
- visual diagnostics for pressure, flow, power and efficiency;
- uncertainty intervals for energy and state estimates.

Future improvements must maintain the same publication boundary: no real FastBlade data, no real facility parameters and no confidential industrial information.
