# Confidentiality boundaries

This repository is a public, synthetic analogue of applied-AI and digital-twin workflows for sensor-heavy hydraulic systems.

The purpose of this document is to make the boundary between public demonstration material and private/confidential material explicit.

## Public repository boundary

The repository may include:

- synthetic data generated by public code;
- generic hydraulic-style variable names;
- illustrative synthetic events and labels;
- public Python source code written for this demo;
- YAML configuration files for synthetic scenarios;
- automated tests for public workflow behaviour;
- generated example figures derived from synthetic data;
- Markdown and HTML reports generated from synthetic data;
- documentation explaining assumptions, limitations, and validation boundaries.

These materials are intended to be safe for public review.

## Material that must not be included

The repository must not include:

- real FastBlade data;
- real University of Edinburgh source code;
- partner or industrial datasets;
- proprietary control logic;
- raw facility sensor exports;
- real hydraulic parameters from restricted projects;
- internal test plans or reports;
- facility-specific diagrams or layouts;
- confidential database schemas;
- private file paths;
- personal data;
- credentials, tokens, passwords, or API keys;
- private calibration values or operational thresholds.

If a file depends on any of the above, it should not be committed to this repository.

## Generated-output boundary

Generated outputs such as CSV files, scenario reports, and local HTML reports are reproducible outputs.

They should normally be ignored by Git and regenerated locally when needed.

Committing generated outputs is acceptable only when they are intentionally selected as public documentation or release assets and have been manually reviewed for confidentiality and interpretation risk.

## Implementation boundary

The implementation is designed to show software structure, not to reproduce a private system.

The public code may show:

- a modular Python package layout;
- a command-line interface;
- synthetic data-generation logic;
- validation checks;
- feature engineering;
- simple energy estimates;
- baseline anomaly detection;
- state classification;
- report generation.

The public code must not encode:

- private facility behaviour;
- proprietary control-system logic;
- real operating envelopes;
- hidden calibration constants from confidential work;
- partner-specific acceptance criteria;
- internal diagnostic thresholds.

## Documentation boundary

Documentation should describe the repository as:

- synthetic;
- illustrative;
- reproducible;
- public-safe;
- useful for method discussion and portfolio review.

Documentation should avoid implying that the repository is:

- a deployed digital twin;
- a calibrated hydraulic simulator;
- a validated monitoring system;
- a real facility replica;
- suitable for safety-critical operation;
- trained or validated on private industrial data.

## Allowed wording examples

Appropriate wording:

```text
This repository demonstrates a synthetic digital-twin-style workflow for hydraulic sensor data.
```

```text
The data and operating behaviours are generated synthetically and are not calibrated to a real facility.
```

```text
The tests verify software behaviour, not operational diagnostic accuracy.
```

Wording to avoid:

```text
This model detects real hydraulic faults.
```

```text
This is a validated FastBlade digital twin.
```

```text
The thresholds match the real facility.
```

## Pre-commit confidentiality checklist

Before committing, check:

- no private data files are staged;
- no generated CSVs from private work are included;
- no screenshots contain private paths or internal names;
- no code contains credentials or tokens;
- no documentation implies real-data validation;
- no file names reveal confidential project details;
- all examples can be regenerated from synthetic configuration files.

Useful commands:

```bash
git status
git diff --staged --name-only
git grep -n "password"
git grep -n "token"
git grep -n "C:\\"
git grep -n "/Users/"
```

These commands are not a substitute for manual review.

## Release boundary

Before a public release, confirm that:

- the README states the synthetic-data boundary;
- validation notes are up to date;
- model-card limitations are up to date;
- generated release assets are synthetic;
- the GitHub release text does not imply operational validation;
- tests and pre-commit checks pass.
